# Kitmux v0.4 — groups inside resource views

V0.4 replaces the separate Groups tab with collapsible sections inside MCPs,
Skills, and Subagents. One resource can appear in several groups while retaining
one definition, package, and set of client overrides.

## Terminal workflow

The five tabs are MCPs, Skills, Subagents, Clients, and Status (`1`–`5`). Group
headers show member counts and effective client availability. Enter or the arrow
keys expand/collapse sections. Search finds matching resources inside collapsed
groups, and resources without memberships appear under Ungrouped.

- `g`: create a group in the current resource type.
- `v`: show group or resource details, including availability explanations.
- `m`: choose a group's members, or a resource's group memberships.
- `a`: choose clients for the selected group or resource.
- `x`: rename a group or edit a resource.
- `d`: remove the selected group or resource. Removing a group preserves its members.
- Space: select rows; repeated appearances of a resource are processed once.

Resource-specific operations remain available: reconnect MCPs, update or roll
back skills, and create, edit, or duplicate subagent definitions.

## Scoped commands

```sh
kitmux mcp group add communication
kitmux mcp group include communication teams slack
kitmux mcp group assign communication --agents codex,claude

kitmux skill group add browser
kitmux skill group include browser agent-browser playwright
kitmux skill group assign browser --agents codex,claude,opencode

kitmux subagent group add review
kitmux subagent group include review code-reviewer
```

The examples require those resource IDs to exist. Group names are independent
within each type. A Skills group cannot contain MCPs or subagents. `list`, `show`,
`rename`, `exclude`, `enable`, `disable`, and `remove` use the same typed prefix.
Unscoped group mutations return guidance to use the resource-specific command.

Availability rules remain unchanged: global resource off and explicit client off
win; otherwise a direct assignment or any enabled assigned group enables the
resource. Disabling one group can leave a member enabled through another group.
The interface reports effective availability, including mixed member states.

## Upgrade from v0.3

```sh
kitmux group migrate --preview
kitmux group migrate --apply
kitmux sync --check
```

Preview is read-only. Apply preserves resource definitions, per-client overrides,
and the enabled/client settings of each group. A mixed group becomes one group
per represented resource type, keeping its original name in each type. Empty
legacy groups become MCP groups, explicitly listed in the preview.

Migration writes a private backup of the original catalog before atomically
replacing it. Applying the migration again is a no-op. The terminal offers the
same preview before its first grouped session with a legacy catalog; cancelling
does not migrate it.

The catalog becomes schema version 3, with scoped keys such as
`mcp:communication`. Older Kitmux binaries cannot load it. Keep the reported
backup and previous binary for rollback; after further resource changes, a
catalog-only rollback would not restore the corresponding native ownership
state. Native credentials and authentication remain local to their clients.

Configuration-as-code callers should migrate first, use typed group commands,
and read scoped group keys from `status --json`. Profile-owned groups remain
separate from other categories and can be represented once per resource type.

## Verification

The release is checked with `make test`, `make sanitize`, and the isolated
installed-client qualification `make test-native`. Regression coverage includes
same-name groups across types, overlapping memberships, migration preservation,
group removal, keyboard navigation, filtering, bulk-action deduplication, and
terminal restoration. Exact release results are recorded in
[the implementation notes](IMPLEMENTATION.md).
